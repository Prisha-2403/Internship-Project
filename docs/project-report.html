01Overview

What the system is, and the principle it is built around.

Sentinel Finance is a decision-support platform for financial crime analysts. It ingests transaction data, engineers behavioural features from each customer's own history, scores every transaction for risk, and gives the analyst a complete, itemised explanation of why a score is what it is. Flagged activity flows into a case management workflow with evidence, notes and an immutable timeline.

The governing principle

The system never asserts that fraud occurred. A risk score means a transaction requires review. Every number shown to an analyst is traceable to a named rule that actually fired, and the machine learning model's influence is deliberately bounded so that a decision affecting a customer can always be justified in plain language.

Design commitments

CommitmentHow it is enforced in the build
ExplainabilityThe displayed score is exactly the sum of the displayed factors. Enforced by an assertion in the scoring engine and by a randomised property test.
Honesty about MLPrecision, recall and confusion matrices are not shown, because no labelled fraud ground truth exists. The model page states this rather than fabricating figures.
No lookaheadEvery feature is computed strictly from history preceding its transaction, so a backfilled score equals the score it would have received live. Verified by test.
AuditabilityThe audit trail is append-only at the database level, not by convention. UPDATE and DELETE are refused by PostgreSQL rules.
PrivacyCustomer identifiers are masked in the serialisation layer, so no endpoint can leak them by omission.
Synthetic data onlyAll demonstration data is generated. No real person, account, device or payment is represented anywhere.

Why the scoring engine is isolated

risk_scoring_service.py has no knowledge of HTTP or the database. It takes a feature snapshot and returns an assessment. That makes it directly unit testable, and guarantees a transaction is scored identically whether the call arrives through the API, a CSV import, or a batch backfill.

Separation of the three transaction tables

TablePurpose

transaction_featuresEngineered behavioural signals. Fully recomputable from the source record.

Keeping these apart means re-running detection rewrites features and scores without ever touching the underlying financial record — an audit requirement, not a convenience.

Audit immutability — enforced, not promised

Migration 0001 installs two PostgreSQL rules that rewrite UPDATE and DELETE on audit_logs into no-ops. This was verified against the live database: an UPDATE, a targeted DELETE, and a bare DELETE FROM audit_logs executed as the table owner were all silently discarded, with the row count unchanged. Neither an application bug nor a compromised application role can rewrite history.

Least-privilege database role

The application connects as a dedicated sentinel role created with NOSUPERUSER, NOCREATEDB and NOCREATEROLE. The bootstrap script requires the superuser password exactly once, to create that role and the database, and never stores it. This was confirmed correct when the test suite — which had tried to create its own test database — was properly refused by PostgreSQL.

05Risk Scoring Engine

Eight deterministic business rules plus one bounded machine learning factor.

Each rule fires only when its condition is met, and contributes a named, positive number of points. The analyst sees every rule that fired, its point value, and a plain-language explanation of the evidence.

Risk bands

BandScoreAnalyst guidance
LOW0 – 29Consistent with established behaviour. No review required.

CRITICAL80 – 100Strong combination of signals. Prioritise for investigation.

The invariant the design protects

business_score == Σ (points of the factors shown to the analyst)

Raw signal strength can exceed 100 when many rules fire together. Rather than clipping — which would leave the displayed factors summing to more than the displayed score — contributions are scaled proportionally onto the 0–100 scale using largest-remainder rounding, and the assessment records that scaling occurred. The explanation panel never shows numbers that fail to add up. This is asserted in the engine itself and verified by a randomised property test across thousands of generated feature combinations.

Why the amount rule takes the stronger of two measures

A customer with near-constant spending has a standard deviation of zero, making the z-score undefined. Under a z-score-only rule, a 50× transaction on such an account would score nothing — precisely the case most worth catching. The rule therefore also evaluates a plain multiple of the customer's average and takes whichever signal is stronger.

06Feature Engineering

24 documented features per transaction; 14 of them feed the model.

No lookahead

Every feature is computed strictly from the customer's history preceding the transaction being described. A score computed during a backfill is therefore identical to the score that transaction would have received live. The test suite asserts this directly: it recomputes features with later rows removed and requires every value to be unchanged.

Computation strategy

Features are produced in two passes. A vectorised pandas pass handles statistics that expanding and rolling windows express directly. A single ordered pass per customer handles the stateful signals — novelty, 30-day distinct counts, the hour-of-day distribution and the location centroid — each of which requires memory of everything seen so far. Time-window counts use NumPy searchsorted on pre-sorted timestamps, which is exact and behaves identically whether the frame holds one customer or ten thousand.

What the model is deliberately not shown

Raw amounts, customer identifiers, and the boolean novelty flags are withheld from the model. It learns from behavioural shape; the novelty conditions are already covered explicitly and transparently by the business rules, where an analyst can see them.

Score normalisation

scikit-learn's decision_function is unbounded and centred on zero, which is impossible to compare across training runs. Output is mapped onto a 0–1 scale using percentile bounds captured at fit time and stored on the model version row. Reusing the training bounds is the point: a transaction scored next week lands on the same scale as one scored during training, so stored scores stay comparable and the threshold does not silently move.

The anomaly threshold is the normalised position of the model's own decision boundary, so "the model considers this anomalous" and "the score is at or above the threshold" are the same statement. On the live model that threshold is 0.7297, with an observed anomaly rate of 3%.

How the model combines with the rules

The model contributes only above its own threshold, and its contribution is capped at 15 points. It appears in the explanation panel as one named factor alongside the business rules, with its own point value — so the final score remains fully attributable while still incorporating a signal the rules alone would miss.

Graceful degradation

If no model has been trained, or its artifact cannot be loaded, the platform continues to operate. The business rules alone produce a complete and fully explainable score; the ML factor simply does not fire. The system never blocks on the model being available.

08On Model Metrics

What the system reports, and what it deliberately refuses to report.

Stated verbatim on the model performance page

"Model performance metrics requiring labeled ground truth are unavailable."

Precision, recall, F1 and confusion matrices require confirmed outcomes for each transaction — a verified record of which were genuinely fraudulent. This platform has no such labels. Any figure presented would therefore be fabricated, so the model page omits them entirely and explains why, rather than producing a number that looks rigorous and is not.

Every failure returns the same envelope, with a stable machine-readable code and a message safe to show a user:

Cross-origin considerations

The three services sit on different origins, which changes assumptions that held on localhost. The session cookie is issued SameSite=None; Secure so it can travel between the frontend and the API; because credentials are involved, a wildcard CORS origin is not permitted, so the API is given the frontend's exact origin.

Operational notes

  • Cold starts. The free API instance sleeps after 15 minutes idle; the next request takes roughly 60 seconds. A scheduled health-check ping removes this entirely.
  • Model artifact. Render's filesystem is ephemeral, so the trained artifact travels with the repository and the registry stores only a filename, resolved against the artifacts directory wherever it runs.
  • Migrations and seeding. Run against the managed database from a developer machine, since the free plan provides no remote shell.

Deliberate scope decisions

The following were considered and consciously excluded, and are recorded as such in the repository rather than left as apparent oversights:

  • Docker and CI. Three managed free tiers carry the stack; container orchestration would add weight before there is anything to orchestrate.
  • WebSockets. The alert centre polls on an interval. For an internal console this is far simpler to make correct and survives reconnects, sleeping laptops and proxy timeouts without dedicated reconnect logic.
  • Redis and Celery. The deployment runs a single API process, so the in-memory rate limiter suffices. Its interface allows a shared store to be substituted without changing callers.
  • PDF report generation. Reports render on screen and export to CSV and Excel.
Closing note

The system's most distinctive property is what it declines to claim. It surfaces transactions for review, shows precisely why, and refuses to present an anomaly as a finding of fraud or to publish accuracy metrics it cannot substantiate. In a domain where a false accusation carries real cost to a real customer, that restraint is the feature.
